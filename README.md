# 色谱数据管理系统（CDS）— 检测数据采集、审计追踪与复核

面向药企质量控制实验室的色谱数据管理模块。目标是解决一类具体的监管缺陷：

> 分析员把不合格的检测结果偷偷删掉重测，只保留合格的那一次；或者手动改积分参数让杂质峰消失。批次放行后才被发现。

系统用 Java 重写采集、审计追踪和复核三个环节，让**每一次进样和每一次重新积分都留下无法抹掉的记录**，并且**复核人能发现它们**。

---

## 三个难点，三层设计

| 难点 | 应对 |
|---|---|
| 厂商软件五花八门 | 只做**一层薄适配器**：厂商文件 → 统一原始进样。适配器不筛选、不判断、不写结果。换厂商只需加一个适配器，防篡改与复核逻辑全部复用。 |
| 删掉不合格的那一针 | **进样是只可追加的事实**，不是可增删的结果。计划先于采数登记；序号由仪器给出。删针会在两处独立暴露：计划缺口 + 序号跳号。 |
| 改积分参数让峰消失 | **没有"更新结果"这个操作**。每次积分都是新版本，父版本指向前一版。版本对比自动列出"消失的峰"，并检测结果是否由不合格穿越到合格。 |
| 复核人时间有限 | 筛查引擎把可疑记录按严重度排序；正常操作落在 INFO 或不出现在列表里。复核人只看顶部少数几条，而不是逐条通读。 |

## 关键机制

### 1. 原始数据在采集时封存

```
厂商文件 --[适配器]--> RawInjection(不可变) --[traceHash]--> 封存
```

- `Chromatogram` 按**定长二进制**编码计算 SHA-256（不是 JSON），改一个采样点即变哈希。
- `RawInjection` 在构造时就校验 `traceHash` 与信号一致，不一致直接拒绝。
- 仓库接口**没有** update/delete，只有 `appendRaw` 与 `addDisposition`。
- 同一序号或同一进样 ID 重复入库会被拒绝——防止厂商侧序号重排后重复导入。

**删针的两种暴露方式：**

1. **计划缺口**：计划 key 唯一标识"批次#样品-R轮次"，重进样不能复用首针的 key。否则"删首针、留重进样"在对账时看起来完全正常——这是最容易犯的建模错误。
2. **序号跳号**：仪器内序号是单调的，账本里缺了 3 号就是缺了。

### 2. 积分只追加版本

```java
integrateFirstTime()  // 仅当无任何版本时可用
reintegrate()         // 必须写原因；新版本挂在链尾，旧版本保留
```

- 积分方法在版本里存**快照 JSON + 哈希**，不是方法 ID 引用。事后改方法库不会改变历史结果的解释。
- 只接受**已批准**的方法版本（有 approvedBy/approvedAt），堵住"临时改个参数试试"。
- `PeakDelta.compute(v1, v2)` 列出消失/新增/变化的峰——这就是"杂质峰不见了"的直接证据。

### 3. 审计链

每条记录包含 `previousHash` 与自身 `recordHash`：

- 改任一字段 → 自身哈希失配
- 删中间一条 → 后续衔接全部失败
- 整条链重算 → 内部自洽，但**头部哈希变化**，外部锚定（WORM/时间戳）可识破

存储接口**没有** update/delete/truncate——不是靠纪律，是靠方法不存在。

### 4. 复核签名绑定记录

Ed25519 签名绑定 `版本结果哈希 + 方法哈希 + 原始进样哈希`：

- 复核后重新积分 → 签名状态变为 `SUPERSEDED`（密码学上仍有效，但不再代表当前结果）
- 复核后篡改原始信号 → `verify()` 重算载荷失败
- 签名无法挪用到别的记录 → 载荷含 versionId

**状态以审计链重放为准，不信任签名表的 status 列。** 直接改数据库把 `INVALIDATED` 改回 `VALID` 也没用——`effectiveStatus()` 从链上重放。

#### SUPERSEDED 与 INVALIDATED 的区别

这是设计上刻意分开的两个概念：

| | 含义 | 密码学 | 含义 |
|---|---|---|---|
| `SUPERSEDED` | 该进样产生了新版本 | 仍有效 | 正常重新积分 |
| `INVALIDATED` | 记录内容被改动 | 失败 | 篡改 |

混为一谈会让审计无法区分"正常调参"与"篡改后伪造复核"。

### 5. 筛查与门槛分离

这两件事**不能**混在一起，否则会出现"队列里尚未复核"被当成告警、导致 `blocking` 恒为真、告警失去区分度：

| | 筛查（`AnomalyDetector`） | 放行门槛（`ReleaseGatekeeper`） |
|---|---|---|
| 回答 | **哪些记录可疑** | **这一批现在能不能放** |
| 输出 | 按严重度排序的发现列表 | 逐项通过/阻断的布尔判定 |
| 用途 | 排序与呈现，把注意力引到少数条目 | 客观条件核实，任何一条不满足即拒绝 |

筛查规则（部分）：

| 代码 | 级别 | 触发条件 |
|---|---|---|
| `PLAN_GAP` | CRITICAL | 计划有、账本无 |
| `SEQUENCE_GAP` | CRITICAL | 仪器序号跳号 |
| `IMPURITY_PEAK_DISAPPEARED` | CRITICAL | 重新积分后杂质峰消失 |
| `SPEC_CROSSING_BY_REINTEGRATION` | CRITICAL | 重新积分使不合格 → 合格 |
| `REVIEW_INVALIDATED` | CRITICAL | 签名后记录被改动 |
| `EXCLUSION_AFTER_RESULT` | HIGH | 先出结果，后声明作废 |
| `REPEAT_WITHOUT_REASON` | HIGH | 重进样未写原因 |
| `REPEATED_REINTEGRATION` | HIGH | 同一进样版本数 ≥ 3 |
| `RAPID_REINTEGRATION` | MEDIUM | 两次重积分间隔 < 10 分钟 |
| `MANUAL_PEAK_EDIT` | MEDIUM | 峰被手工增删/调整 |
| `REVIEW_SUPERSEDED` | INFO | 历史版本签名被取代（正常流程） |

**发现不可删除。** 复核人只能"接受并说明"（`FindingDisposition`），异常仍留在列表里，只是多了一条可审计的意见。放行门槛据此判断"是否已解释"——但"接受并说明"这个动作本身进审计链。

### 6. 规范化：一切哈希的基础

`Json.canonical()` 是系统里所有哈希与签名的唯一输入格式。确定性来自：

1. record 字段按声明顺序
2. Map 键按字典序（domain 层用 `TreeMap`）
3. 浮点用最短往返表示，与区域设置无关
4. null 字段保留
5. **只有 record 组件参与序列化**——关闭 getter/is-getter/字段自动发现

第 5 点很关键：`isUsable()`、`isImpurity()` 这类辅助方法如果被当成属性写进 JSON，**改个方法名就会改变历史记录的哈希**，等于让"重构代码"变成"篡改历史"。`CanonicalizationGoldenTest` 用固定哈希钉住格式。

```bash
# 需要 JDK 21
export JAVA_HOME=$(/usr/libexec/java_home -v 21)   # 或 Homebrew 的 openjdk@21

gradle test     # 66 个测试
gradle run      # 演示：三种造假手法 → 被捕获 → 放行被阻断
```

## 生产化时还需要补的

本仓库是**可运行的设计与验证**，不是可直接投产的系统。上线前至少还需要：

- **持久化**：审计存储落在 append-only 介质（WORM、只追加表 + 拒绝 UPDATE/DELETE 的触发器），业务表同理
- **外部锚定**：定期把链头哈希写入法律时间戳/对象锁/WORM 桶，使"整条链重写"也不可行
- **密钥管理**：操作员私钥放 HSM 或智能卡，永不离开硬件；本仓库用进程内密钥对模拟，签名/验签路径与生产一致
- **时间的可信来源**：时间戳应来自受控时钟，本仓库用可注入时钟便于测试
- **真实适配器**：ANDI/AIA（netCDF）、Agilent .D、Waters .raw、Shimadzu .lcd 等
- **并发的正确性**：内存实现用 `synchronized` 保证单进程一致；分布式部署需要基于数据库事务或单写者队列
- **法规映射**：21 CFR Part 11 / 中国 GMP 附录《计算机化系统》的逐条对照矩阵

## 已知的设计取舍

- **峰检测器是教学级实现**，不是工业级积分器。它刻意做到"相同输入 → 逐点相同输出"，因为监管的核心诉求是可复现。接口与产物结构与工业实现一致，便于替换。
- **`slopeSensitivity` 只影响峰边界，不影响峰是否存在**。早期实现把它误用作峰值判据，结果峰顶导数恒接近 0，阈值一调高所有峰都被滤掉——参数语义错误会让审计规则误报/漏报。峰是否存在由 `minHeight` 控制，这才是"改参数让峰消失"的真实载体。
- **重进样不要求在计划中预先登记**（REPEAT 类型），因为临时复测确实存在；但它必须带原因，且会触发 `REPEAT_WITHOUT_REASON`。
- **作废是合法操作**。系统不禁止作废，只要求它可见、有原因、且"作废后再重测"能被识别。
