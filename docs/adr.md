# 架构决策记录

记录本系统里那些**看起来可以简化、但一简化就会开口子**的设计决定。每条都写清楚：
当初的问题是什么、怎么决定的、如果改动会付出什么代价。

后人若要推翻其中任何一条，请先读完"代价"。

---

## ADR-001 原始进样只可追加，接口上没有删除

**问题**：分析员删掉不合格那一针，只提交合格的重测。

**决定**：`LabRepository` 不提供 update/delete 原始进样的方法。作废通过追加
`InjectionDisposition` 表达，原始记录仍在。

**代价**：存储只增不减，需要归档策略。这个代价是刻意的——"删得掉"本身就是缺陷来源。

---

## ADR-002 计划 key 唯一标识"一次进样"，不是"一个样品"

**问题**：如果重进样复用首针的 plannedKey，那么"删首针、留重进样"在按 key 对账时
看起来完全正常，`PLAN_GAP` 永远不触发。

**决定**：plannedKey 格式为 `批次#样品-R轮次`。这是本项目早期真实踩过的坑：
最初的实现用 `批次#样品`，演示场景里删针**没有**被计划对账发现，只有序号跳号报警。

**代价**：登记计划的调用方必须知道轮次。这是必须的——轮次正是"第几次进样"这个事实本身。

---

## ADR-003 重新积分只能追加版本，方法参数存快照

**问题**：改积分参数让杂质峰消失，事后无法还原"当初是怎么积的"。

**决定**：
- `reintegrate()` 必须给原因，产生 v(n+1)，`parentVersionId` 指向前一版；
- 方法在版本里存**快照 JSON + 哈希**，不是方法 ID 引用。

**代价**：每次积分存一份完整方法 JSON。相比"引用方法 ID"略占空间，
换来"事后改方法库不会改变历史结果的解释"。

---

## ADR-004 规范化 JSON 只序列化 record 组件

**问题**：Jackson 默认会把 `isUsable()`、`isImpurity()` 这类 is-getter 当成属性写进 JSON。
结果是：**改一个辅助方法的名字，就会改变历史记录的哈希**，等于让"重构代码"变成"篡改历史"。

**决定**：序列化方向关闭 getter / is-getter / 字段自动发现；反序列化方向保留字段可见性
（否则 record 组件无法还原）。`CanonicalizationGoldenTest` 用固定哈希钉住格式。

**代价**：Jackson 版本升级需要跑 golden test 比对。这是必须的——升级改哈希 = 历史签名全部失效。

---

## ADR-005 所有 canonicalForm 走同一条路径

**问题**：早期多个 record 用 `Canon.kv()` 手写 canonicalForm，而哈希路径用 `Json.canonical()`。
同一个对象有两套规范化表示——**方法哈希与内容可以脱钩**。
`IntegrationMethod` 的自洽测试发现了这一点：`methodHash` 存在版本里，但
`method.contentHash()` 算出的是另一个值。

**决定**：删掉全部自定义 `canonicalForm()`，统一走 `Canonical` 的默认实现（Json）。
唯一的例外是 `Chromatogram`：它用定长二进制编码，因为 36000 点走 JSON 会让哈希成为瓶颈。

**代价**：`Canonical` 接口的存在意义从"允许自定义表示"退化为"提供默认实现"。
这是对的：表示方式的多样性是完整性漏洞的温床。

## ADR-006 签名状态以审计链重放为准，不信任签名表的 status 列

**问题**：签名表里的 `status` 是一个可以被 DBA 直接 UPDATE 的列。
把它改回 `VALID`，过期签名就"复活"了。

**决定**：`effectiveStatus()` 从审计链重放——链是 append-only 且逐条哈希串联的。
签名表的 status 降级为展示用缓存。

**代价**：每次读状态要扫一遍链。数据量大时应加索引或增量重放缓存，但**权威来源**不能变。

---

## ADR-007 SUPERSEDED 与 INVALIDATED 必须分开

**问题**：最初的实现把"重新积分后旧签名不再代表当前结果"和"记录被篡改"都记成 INVALIDATED。
后果是审计无法区分**正常的重新积分**与**篡改后伪造复核**——而对合规调查来说，
这两者的处置完全不同。

**决定**：
- `SUPERSEDED`：出现了新版本。密码学上签名**仍然有效**（它确实签的是那一版）。
- `INVALIDATED`：被签的记录内容变了。密码学验证**失败**。

**代价**：状态机多一个态。但少这个态，审计报告就无法回答"到底是正常调参还是篡改"。

---

## ADR-008 筛查（排序）与门槛（放行）是两个机制

**问题**：最初把"某条结果还没复核"也作为筛查发现。结果复核队列里每一条都触发它，
`blocking` 恒为真，告警失去区分度——等于没有告警。

**决定**：
- `AnomalyDetector` 回答"**哪些记录可疑**"，输出按严重度排序的列表；
- `ReleaseGatekeeper` 回答"**这一批现在能不能放**"，输出逐项通过的布尔判定。

**代价**：两个类、两套概念。但混在一起的代价是告警失效，那更贵。

---

## ADR-009 结果由不合格变合格，要区分"峰还在"与"峰没了"

**问题**：验收测试发现，正当的方法修正（补上主峰保留时间归属）也会让结果从超限变为合格。
若一律判 CRITICAL，复核人会对告警麻木——这正是"时间有限"约束下最怕的事。

**决定**：
- 峰仍存在、仅归属/类型变化 → MEDIUM（"需确认归属规则改动有理有据"）；
- 有峰消失 → CRITICAL。

**代价**：规则更复杂。但没有这个区分，"正常参数调整确实存在"这一前提就无法满足。

---

## ADR-010 作废会真实触发签名失效，且"看护"必须被接上

**问题**：`sweepInvalidations()` 和 `onDispositionChanged()` 写好后**没有任何地方调用**。
注释说"打开复核界面时运行"，但实际不生效——典型的纸面机制。
`HousekeepingWiringTest` 专门验证每条失效路径都被真实触发。

**决定**：
- 作废/恢复时由 `IngestService` 主动调用 `housekeeping.onDispositionChanged()`；
- 筛查开始时执行一次 `sweepInvalidations()`。

**代价**：`IngestService` 需要可选依赖 `Housekeeping`（用 `bindHousekeeping` 注入，
避免构造期循环依赖）。任何"注释里说会运行"的机制，都必须有测试证明它真的运行。

---

## ADR-011 放行必须重新评估，不能用界面上那份

**问题**：`markReleased` 若直接信任传入的 `ReleaseGate`，那么"用户看到可放行 → 有人又积了一版
→ 用户点确认"这个窗口里，过期的评估结果仍然放行。这是典型的 TOCTOU。

**决定**：`markReleased` 内部重新 `evaluate()`，并与用户看到的评估做**语义摘要**比对
（`eligibilityDigest()`），不一致即拒绝。

**代价**：放行时有两次评估开销。另注意摘要比对**不能**用 `checks.equals()`——
Check 的 detail 含"已校验 N 条审计记录"，而每次评估自身会写审计，N 会变。
用会自然漂移的值做相等比较，会导致永远无法放行（本项目真踩过这个坑）。

---

## ADR-012 峰检测器自己实现，可复现优先于黑盒

**问题**：厂商算法的版本漂移是"同一数据两次积分结果不同"却无法解释的常见根源。

**决定**：自己实现确定性峰检测器。给定相同信号 + 相同参数快照，任何人任何时候得到逐点相同的峰表。

**代价**：教学级积分器，不是工业级。接口与产物结构与工业实现一致，便于替换。
关键教训：早期把 `slopeSensitivity` 误用作峰值判据，峰顶导数本就接近 0，
阈值一调高所有峰都被滤掉。参数语义错误会让审计规则误报/漏报——
`minHeight` 才控制"峰是否存在"。
